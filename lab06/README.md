## 3. План експерименту, метрики та правило рішення

Вкладена CV: **5 outer × 3 inner**, StratifiedKFold(shuffle=True, random_state=42).
На кожному outer-train обидві гілки отримують одні й ті самі inner-індекси; переможці вибираються за середнім inner AP,
перевчаються на outer-train і оцінюються один раз на відповідній outer-validation.
OOF: кожен train-ID отримує рівно один відкладений прогноз від кожної гілки й DummyClassifier(strategy='prior').

Основна метрика — **Average Precision**, бо позитивні становлять близько десятої частини потоку; AP оцінює ранжування позитивних.
Додаткові — ROC-AUC, F1, precision, recall, balanced accuracy, Brier і log loss. Усі порогові метрики мають фіксований поріг 0.5.
Нульовий F1 baseline явно обробляється через zero_division=0, без приховування попереджень.

До запуску задано $d_j=AP_{AutoML,j}-AP_{Manual,j}$ та **ε=0.01 AP**.
Якщо середня d>ε, обрати AutoML; якщо d<−ε — Manual; інакше послідовно: менший серіалізований Pipeline,
менший p95 single-object latency, потім Manual. Перебування в зоні цього рішення не доводить статистичну еквівалентність.

## 4. Preprocessing та простори пошуку

Обидві гілки: `SimpleImputer(median, keep_empty_features=True) → StandardScaler → estimator`.
Кожен imputer і scaler навчається **всередині кожного inner fit**. Сталі колонки збережено: StandardScaler безпечно дає нуль;
прихованого відбору ознак немає. Хоч дерева не потребують scaling, той самий контракт робить гілки зіставними.

| Manual-сімейство | Конфігурації, задані до outer CV |
|---|---|
| LogisticRegression | C ∈ {0.01, 0.1, 1, 10}, max_iter=5000 |
| RandomForest | 64 дерева; (depth, min_leaf): (5,1), (10,1), (None,1), (None,3) |
| HistGradientBoosting | (lr, iter, leaves): (.03,100,7), (.1,100,7), (.1,100,15), (.1,150,31); early_stopping=False |

FLAML 2.3.6 використовує п'ять сімейств: lrl2, rf, extra_tree, histgb, kneighbor.
Повний простір доменів і початкові точки задано в [`experiment.py`](experiment.py), машинозчитувана копія —
[`search_contract.json`](results/search_contract.json). Для кожного параметра перше значення домену є init_value.
Пошук — **готовий FLAML CFO**, не власна випадкова генерація.
`max_iter=12`, `metric='ap'`, `eval_method='cv'`, `learner_selector='roundrobin'`, `log_type='all'`,
`sample=False`, `auto_augment=False`, `ensemble=False`, `skip_transform=True`, `retrain_full=True`, `n_jobs=1`.

Власні класи BaseEstimator обгортають sklearn Pipeline, щоб FLAML не робив preprocessing до inner split.
`FrozenCV` повертає точні збережені індекси й підтримує split(X) без y. API перевірено за
[документацією FLAML](https://microsoft.github.io/FLAML/docs/Use-Cases/Task-Oriented-AutoML/).
Будь-який failed trial, NaN loss або неповний бюджет зупиняє запуск, а не зникає з таблиці.

## 12. Інженерний висновок

Обидві процедури перевищили baseline. Доведеної практичної переваги AutoML за AP у наперед заданому сенсі немає:
0.002836 < 0.01. AutoML обрано через менший файл, а не лише через найвище середнє AP.
Вища AP поєднується з нижчим пороговим recall і гіршим Brier — ці аспекти не можна підміняти один одним.

Manual-сімейство стійке, AutoML-сімейство нестійке до seeds; малі train-розбіжності не спростовують цього факту.
Початкове порушення holdout виправлено новим непереглянутим джерелом і regression test, а не косметичною зміною seed.
До ЛР № 7 передано Extra Trees Pipeline та обмеження: невелика історична колекція, відсутність writer-ID,
невідомі нові сканери/автори, фіксований поріг, малий бюджет пошуку та необхідність людини при OCR-рішенні.
Подальша калібровка/поріг потребує нової валідації; поточний test для цього повторно не використовувати.
